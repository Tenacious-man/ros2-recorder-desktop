# 实时消息时间戳对比

数据分析页实时显示本机当前系统时间（Unix 秒），可查看各话题最新消息与本机系统时间或其他话题的毫秒差值。

## 使用

1. 在“消息环境”加载当前 ROS 2 环境及自定义消息类型，确保与发布端的 Domain 一致。
2. 进入“数据分析”，点击“选择话题”，在弹窗中按消息类型筛选、搜索 / 刷新并勾选相机、毫米波雷达、激光雷达等话题。点击“确认选择”后弹窗关闭，主表只显示这些已选话题。初次进入时主表为空，不铺开全部发现话题。
3. 点击“开始监听”。比较基准默认为“本机系统时间（接收时）”，也可以选一个已勾选的话题。监听期间可重新打开“选择话题”修改，确认后才更新订阅。仍保留的话题继续显示原来的最新消息，新增话题等待新消息。
4. 查看最新 header 时间、本机接收时间（秒，小数点后九位纳秒）及相对基准差值（ms）。切换基准会用表中保留的消息立即重算。
5. “停止监听”释放订阅并保留最后的显示值。重新开始时清空旧结果，等待新消息。

主表支持按住话题行拖动，调整显示顺序。手动排序保留在本次运行中，时间戳更新、话题刷新及重新确认选择不会重置仍保留话题的顺序；新增话题追加到末尾。拖动不重启订阅、不更换当前比较基准。

选择本机作为基准时，每一行用该条消息进入本机订阅回调时的系统时间计算差值。页面顶部的当前时间继续刷新，表中的接收时间和差值随新消息更新。

```text
差值(ms) = (本话题最后收到消息的 header 纳秒 - 本机收到该条消息的 Unix 纳秒) / 1,000,000
```

选择话题作为基准时，用该话题最新消息的 header 计算差值。

```text
差值(ms) = (本话题最后收到消息的 header 纳秒 - 基准最后收到消息的 header 纳秒) / 1,000,000
```

例如，相机基准为 `100.000000000`，雷达为 `100.007250000`，雷达显示 `+7.250 ms`；激光雷达为 `99.996500000`，显示 `-3.500 ms`。

“最新”按本机实际收到并处理消息的顺序定义。即使新到的消息时间戳小于上一条，也更新为新到的值，不保留最大时间戳。零 / 无效 header 或解码失败的最新消息会使本话题差值暂不可用，不继续冒用之前的有效时间。基准无有效时间时，所有差值显示“—”。

超过 2 秒没有新消息会显示未更新多久，时间戳和差值仍按最后收到的消息保留；低频话题也可能正常出现该状态。停止后明确标记保留最后消息。消息类型缺失、消息没有 header、尚未收到消息等情况分别显示原因。

## 通信设置与对照

1. 在“对照监听设置”选择订阅方式、保留帧数和监听时长。建议对照时将每轮设为相同的时长，例如 30 秒。默认采用 Best Effort、保留 5 帧、沿用消息环境和手动停止。Reliable 需要发布端提供 Reliable。
2. “套用同机大点云建议”设为 Best Effort、保留 2 帧、Fast DDS 共享内存 8 MiB 并保留 UDP。监听端设置保存在本机，下一轮启动时加载。对照备注可记下发布端配置。
3. 停止第一轮并点击“将本轮设为基线”。换一组设置监听同一话题，在“查看通信对照”中并排检查基线和本轮。基线保留在本次应用会话。

频率从第一帧收到后开始计算。最长接收间隔包含最后一帧到快照时的等待时长。帧龄等于本机接收时间减消息 header 时间，需要确认双方时钟使用同一基准。最大帧龄覆盖本轮有效时间戳，P99 取最近 2048 条有效帧龄。用相同话题、ROS Domain、时长和负载做对照。

## 通信环境模块

进入管理员模式后，在侧栏打开“通信环境”。“DDS 与共享内存”可选共享内存加 UDP 或仅 UDP，设置 SHM 段大小和 UDP 接收缓冲请求值。“设为当前账户默认”把 Fast DDS XML 和 Linux 用户会话环境项写入用户配置目录。重新登录后，由用户会话启动的 Fast DDS 程序可以继承。当前终端或 SSH 可复制加载命令后启动程序。系统服务、容器和其他账户需要在各自启动环境加载 XML。撤销账户默认项后，导出的 XML 和用于显式加载的 XML 可以继续使用。

“环境检查与配置参考”包括当前环境、运行进程、话题 QoS、按用途建议和参数说明。部署后用“运行进程”核对实际的 DDS 库和共享内存映射，用“话题 QoS”核对节点的发布和订阅设置。

UDP 接收缓冲是 Fast DDS 向 Linux 请求的值，受本机显示的内核上限约束。请求超过上限时可复制临时调整命令，在接收机终端运行后再测。启用了 ROS 仅本机通信时，Fast DDS 可能额外启用默认共享内存，需从运行进程核对实际传输。

## 范围

与本机比较时，差值包含消息传输和接收处理耗时，可用于观察授时偏差。解读差值时需确认 header 使用的时钟基准及其对应的采样时刻。话题间比较各自最后收到的消息，发布频率、消息到达先后和订阅丢包都会影响结果。

## 实现与复用

- 直接使用 ROS 2 原生 `rclpy` 的 raw 订阅和序列化接口，复用当前软件的话题发现、环境加载与进程管理；未实现新的 DDS 通信层。
- 对声明首字段为标准 `std_msgs/Header` 的 CDR1 消息，将时间字段的 12 字节序列化前缀交给原生 `builtin_interfaces/Time` 解码器，避免完整解码图像、点云和轨迹数组。其他字段布局或序列化编码使用原生全消息解码，不猜测偏移。这是只提取时间字段，不验证整个消息体完整性的优化。
- 每个话题只存一条最新时间快照，界面约每秒刷新 10 次，不积累消息体或历史曲线。浅层 best-effort、volatile QoS 面向当前传感器数据；不主动拉取 transient-local 的历史样本，也不保证收到所有发布消息。
- 监听与录制互斥；监听前暂停既有频率检测订阅，停止后恢复，避免同时建立两套大数据订阅。应用退出时停止辅助进程并清理临时控制文件。

参考的现成组件与项目：

- [ROS 2 rclpy](https://github.com/ros2/rclpy)：直接复用 raw 订阅、原生序列化和执行器。
- [ROS 2 common_interfaces](https://github.com/ros2/common_interfaces)：使用标准 Header / Time 类型定义与生成的类型信息。
- [ROS 2 message_filters](https://github.com/ros2/message_filters)：调研过其匹配 / 缓存功能；本需求仅比较最后收到的消息，不需要加入同步匹配依赖。
- [PlotJuggler rosx_introspection](https://github.com/facontidavide/rosx_introspection)、[plotjuggler_bridge](https://github.com/PlotJuggler/plotjuggler_bridge)：参考避免无谓处理大数组、保留原始时间戳的思路；当前版本没有内嵌这些项目，也没有声称复用了其代码。

## 验证

测试覆盖相机 / 雷达 / 激光雷达混合消息类型、真实 ROS raw 订阅、整数纳秒精度、正负差值与基准切换、新消息时间倒退、零 / 无效时间、缺失消息类型、没有 header、陈旧快照拒绝、动态增减订阅、录制互斥和退出清理。真实发布测试使用隔离 Domain，不连接现场设备。

选择弹窗测试覆盖确认后仅显示已选行、取消不改变选择、搜索结果外保留勾选、刷新保留选择草稿、监听中修改仅在确认后应用、保留原基准及未移除话题的最新值，以及确认清空后显示空状态。

“消息类型”下拉框按完整 msg 类型筛选，包含当前发现的自定义类型，常见图像 / 点云类型优先列出。类型条件与关键词搜索同时生效；切换类型或搜索不会取消已勾选的话题，计数会提示筛选外的选择。刷新后保留当前类型条件，即使该类型暂时未发现也不自动切回“全部消息类型”。同为 PointCloud2 的激光雷达与毫米波话题可继续用名称关键词区分。

“全选当前结果”和“取消当前结果”只操作符合当前消息类型及关键词筛选的话题，筛选外的话题保持原来的勾选状态；类型未知或冲突的话题不会被批量勾选。没有筛选条件时操作整个列表。批量操作只修改弹窗内的选择草稿，点击“确认选择”后才应用到监听，取消弹窗仍保留原来的选择。
